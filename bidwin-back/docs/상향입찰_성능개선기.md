# 상향 입찰 성능 개선기 (Redis 도입)

## 1. 문제 인식 — 검증 안 된 걱정

상향 입찰(경매에 가격을 올려 부르는 방식)은 여러 사람이 동시에 같은 경매에 입찰할 수 있다. 코드를 처음 봤을 때 든 생각은 "인기 경매에 입찰이 몰리면 이 로직이 버틸까?"였다. 그런데 이 걱정이 실제로 근거가 있는 건지, 그냥 느낌인지 구분이 안 됐다. 그래서 실제로 부하를 걸어서 확인해보기로 했다.

## 2. 현재 동시성 제어 구조 — 조건부 UPDATE

입찰 확정은 아래와 같은 형태의 조건부 UPDATE로 처리된다.

```sql
UPDATE auction
SET current_price = :price
WHERE id = :auctionId
  AND current_price < :price - :bidUnit
```

한 문장으로 "현재가보다 높은가"를 비교하고 갱신까지 끝낸다. 영향받은 행이 1이면 승리, 0이면 패배다.

조건부 UPDATE가 비관적 락보다 유리한 이유는 **락을 들고 있는 시간**이다. 비관적 락은 `SELECT ... FOR UPDATE`로 락을 잡은 뒤 애플리케이션 메모리에서 값을 비교하고 다시 `UPDATE`를 보내는 2번의 DB 왕복이 필요하고, 그 사이 자바 코드가 도는 시간까지 전부 락을 들고 있다. 조건부 UPDATE는 비교와 갱신이 DB 엔진 안에서 한 번에 끝나 왕복이 1번뿐이고, 락을 들고 있는 시간이 그 한 문장의 실행 시간으로 줄어든다. 뒤에서 기다리는 사람이 있다면, 이 차이가 대기열 전체의 대기시간에 그대로 곱해진다.

## 3. 가설을 실측으로 뒤집은 과정

처음엔 "동시 입찰이 몰리면 DB 커넥션 풀이 고갈되고, 락 경합으로 타임아웃이 난다"고 가정했다. k6로 부하를 걸어보니 실제로 동시성이 오르면 응답 시간이 급격히 나빠지긴 했다. 그런데 원인을 커넥션 풀 크기라고 단정하기 전에, 풀 크기를 10에서 30으로 늘려서 A/B로 비교했다 — **개선이 없었다.** MySQL의 `Innodb_row_lock_time_max`도 실제 락 대기 시간이 타임아웃(3초)에 도달한 적이 거의 없다는 걸 보여줬다.

즉 "커넥션 풀 고갈"이라는 가설은 틀렸다. 커넥션 풀을 늘리는 건 병목이 어디서 대기하는지 자리를 옮기는 것일 뿐, 근본 원인을 건드리지 못했다.

## 4. 진짜 병목 — 낭비되는 왕복과 단일 행의 물리적 한계

실제로 응답이 느려지는 원인을 뜯어보니 두 가지였다.

**첫째, 질 게 뻔한 요청도 DB를 3번 왕복한다.** 낮은 가격을 부른 입찰도 일단 조건부 UPDATE를 한 번 시도하고, 실패하면 실패 원인을 정확히 알려주기 위해 경매 재조회 + DB 서버 시각 조회를 추가로 한다. 동시 입찰 상황에서는 대다수(실측 기준 80% 이상)가 결국 지는 입찰인데, 이 다수가 매번 3번의 DB 왕복을 그냥 버리고 있었다.

**둘째, 진짜 경쟁자들 사이의 처리는 근본적으로 직렬화된다.** 같은 행을 동시에 갱신할 수 없는 건 InnoDB의 물리적 특성이라, 캐시나 튜닝으로 우회할 수 없다. 소수의 진짜 경쟁자가 있다면, 그들은 결국 한 명씩 순서대로 처리돼야 한다.

## 5. 해결 방안 비교

- **로컬 인메모리 캐시**: 서버가 한 대뿐인 지금은 충분하지만, "분산 환경을 고려하라"는 요구사항을 만족하지 못한다. 서버가 여러 대가 되는 순간 각 인스턴스가 서로 다른 캐시 값을 들고 있게 된다.
- **Kafka 기반 완전 직렬화**: 경매별로 파티션을 나눠 컨슈머 하나가 순서대로 처리하면 락 경합 자체가 없어진다. 하지만 응답이 비동기가 되어 지금의 동기 API 계약을 깨야 하고, 프론트엔드까지 걸친 변경이 필요하다. 1개월 프로젝트 스코프와 실측으로 확인된 필요성(아래 7번 참고) 대비 비용이 크다고 판단해 제외했다.
- **Redis**: 분산 환경에서도 하나의 값을 공유할 수 있고, Lua 스크립트로 원자적 연산을 쓸 수 있어 절충안으로 채택했다.

## 6. 설계와 구현 — 실패에서 배운 두 번째 버전

**1차 시도**는 단순했다: Redis에 캐싱된 현재가를 GET으로 확인해서 확실히 낮은 가격은 걸러내고, 트랜잭션이 커밋된 후에 캐시를 갱신했다. 그런데 동시성을 올려서 다시 재보니 개선이 거의 없었다. 원인은 캐시 갱신이 "커밋 후"에야 일어난다는 데 있었다 — 버스트 상황에서 짧은 시간에 몰린 요청들이 전부 같은(오래된) 캐시 값을 보고 동시에 필터를 통과해버려서, MySQL 앞에서 다시 경합이 재현됐다.

**2차 시도**는 비교와 갱신을 Lua 스크립트로 원자적으로 묶었다.

```lua
local current = tonumber(redis.call('GET', KEYS[1]) or '0')
if tonumber(ARGV[1]) > current then
    redis.call('SET', KEYS[1], ARGV[1])
    return current  -- 이겼을 때 이전 값을 반환 (되돌릴 때 필요)
else
    return -1        -- 졌음
end
```

이겼다고 판정된 요청만 MySQL로 넘어간다. 다만 Redis에서 이겨도 MySQL에서 다른 이유(본인 경매, 경매 종료, 그 사이 진짜 승자 등장)로 최종 실패할 수 있어, 이 경우엔 보상 트랜잭션으로 캐시를 이전 값으로 되돌린다.

## 7. 재검증 — 실제 배포 스펙으로 다시 측정

초기 테스트는 로컬 Docker MySQL의 기본 커넥션 풀을 그대로 썼는데, 실제 배포 목표가 t3.micro(vCPU 2)라는 걸 감안하지 않은 채였다. HikariCP 권장 공식(`core_count * 2 + spindle`)에 따라 풀 크기를 5로, 톰캣 스레드도 t3.micro의 RAM(1GiB) 제약을 감안해 100으로 낮춰 다시 측정했다.

그 결과, 로컬 환경 기준으로 "VUS 100까지는 멀쩡하다"고 봤던 것과 달리 **VUS 10~20 사이에서 이미 응답시간이 절벽처럼 나빠지기 시작했다** — 처음 가정했던 것보다 훨씬 낮은 동시성에서 문제가 시작된다는 뜻이었다. 이 기준으로 Redis 적용 전후를 다시 비교했다(각 20초, VUS 10/20/40/60/80/100, 총 12회, 약 7,500건 요청).

| VUS | med(전) | med(후) | p95(전) | p95(후) | p99(전) | p99(후) |
|---|---|---|---|---|---|---|
| 10 | 11.6ms | 11.7ms | 116.9ms | 354.1ms | 1.45s | 1.47s |
| 20 | 8.0ms | 6.0ms | 2.44s | 2.42s | 2.65s | 2.64s |
| 40 | 12.7ms | 5.5ms | 4.99s | 5.06s | 5.21s | 5.26s |
| 60 | 8.5ms | 4.5ms | 7.73s | 7.46s | 7.9s | 7.68s |
| 80 | 10.3ms | 4.8ms | 10.56s | 10.19s | 10.71s | 10.31s |
| 100 | 10.0ms | 7.8ms | 12.74s | 12.85s | 12.86s | 12.95s |

전체 구간에서 락 타임아웃/서버 오류(409, 5xx)는 전후 모두 0%였다.

**대다수가 체감하는 지연(중간값)은 40~55% 줄었다.** 반면 p95/p99, 즉 꼬리 지연은 거의 그대로다 — 이건 설계상 당연한 결과다. Redis 필터는 "질 게 뻔한 요청이 DB를 낭비하는 것"만 막도록 설계됐고, "진짜 경쟁자끼리의 처리 속도"는 원래 처음부터 다른 문제였다.

부가적으로, VUS 80~100 구간에서 톰캣 스레드 풀(100개)이 79~100%까지 차는 걸 실측으로 확인했다. 소수의 진짜 경쟁자가 MySQL 락을 기다리며 스레드를 오래 붙잡고 있으면, 그 여파로 원래는 즉시 끝나야 할 "낮은 가격" 요청들도 스레드를 못 받아 함께 느려질 수 있다는 걸 보여준다.

## 8. 한계와 다음 단계

이 개선이 모든 걸 해결한 건 아니다. 명확히 인정할 부분은:

- **진짜 경쟁자 간의 처리 속도는 그대로다.** 이걸 풀려면 캐시가 아니라 아키텍처를 바꿔야 한다 — 예를 들어 경매별로 단일 컨슈머가 순서대로 처리하는 큐(Kafka, 혹은 Redis Stream으로도 유사하게 구현 가능) 구조로 가면 락 경합 자체가 사라진다. 하지만 이건 지금의 동기 API 응답 방식을 비동기로 바꿔야 하는 문제라, 프론트엔드 스펙까지 건드려야 한다.
- **극단적인 동시성(수백 명이 한 경매에 20초 안에 몰리는 수준)에서는 이 개선으로도 부족하다.** 실측해보니 이 경우 응답시간이 30초를 넘어가며, 이는 실사용자 관점에서 사실상 장애다.

다만 이 프로젝트의 실제 트래픽 규모를 고려하면, 이 정도로 극단적인 동시성이 일어날 가능성은 낮다고 판단했다. "완전히 해결"이 아니라 "실측으로 확인된 문제(DB 왕복 낭비)만 해결하고, 근본적인 한계는 인지한 채로 스코프에서 제외했다"는 것이 이번 개선의 정확한 위치다.

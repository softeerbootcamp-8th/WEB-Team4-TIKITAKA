# 경매 제목 검색 개선: MySQL n-gram 전문 검색 검토

## 문서 상태

- 상태: 실험 종료 — 현재 구현은 도입하지 않음
- 대상: 경매 목록 제목 검색
- 기준 환경: MySQL 8.4, InnoDB, `utf8mb4_0900_ai_ci`
- 기준 데이터: 전체 경매 100만 건, 활성 경매 30만 건

## 결론

전체 `auction` 100만 건에 MySQL InnoDB
`FULLTEXT ... WITH PARSER ngram` 인덱스를 추가하는 현재 구현은 도입하지
않는다.

기능 플래그 뒤에 구현하고 합성 데이터로 검증한 결과, 0건·희귀·중빈도
검색은 개선됐지만 모든 제목에 공통인 극단적 고빈도 검색은 전체 타입 최신순
후보 조회가 약 0.8초에서 2.5초로 악화됐다. 고빈도 FULLTEXT 계획 하나에서
cgroup 메모리가 약 2.11GiB 증가했고, 반복 측정 과정에서는 `mysqld`가 약
6.73GiB의 익명 RSS를 사용한 상태로 Docker VM 전역 OOM이 발생했다.

기능 플래그를 꺼도 FULLTEXT 인덱스의 저장 공간과 경매 쓰기 시 색인 비용은
남는다. 따라서 현재 릴리스는 기존 `LIKE` 검색을 유지하고, 실험 코드와 V18
migration은 배포 대상에 포함하지 않는다. 이 결과는 n-gram 자체가 항상
부적합하다는 의미가 아니라, 전체 이력 테이블을 직접 검색하는 현재 구조가
운영 안전성 기준을 충족하지 못했다는 의미다. 세부 실측과 OOM 포렌식은
[구현 진행 로그](./auction-search-ngram-implementation-design.md#구현-진행-로그)에
기록한다.

다음 검토안은 활성 경매만 물리적으로 유지하는 검색 전용 테이블이다. 격리된
DB에서 실제와 유사한 한글·Zipf 제목 분포, 명시적인 쿼리 메모리 상한과
컨테이너 메모리 상한을 적용한 뒤 다시 비교한다. 그 구조로도 목표를 충족하지
못하거나 고급 검색 요구사항이 생기면 Elasticsearch를 검토한다.

현재 요구사항은 30자 이내의 경매 제목에 대한 부분 문자열 검색이다. 오타
교정, 형태소 분석, 자동완성, 복합 랭킹과 같은 고급 검색 기능은 현재 범위에
포함되지 않는다. 실험 전에는 별도 검색 클러스터와 데이터 동기화 체계가
필요한 Elasticsearch보다 기존 MySQL 안에서 역색인을 사용하는 n-gram
전문 검색의 운영 부담이 낮다고 판단했다.

그러나 성능·안정성 검증 결과, 전체 이력 테이블을 직접 색인하는 현재 구조는
고빈도 검색의 성능과 메모리 안전성 기준을 충족하지 못했다. n-gram의 부분
문자열 검색 적합성은 유효하지만, 새로운 저장 구조와 운영 제한을 적용한 뒤
별도 실험으로 다시 판단해야 한다.

## 배경

현재 제목 검색은 다음과 같은 선행 와일드카드 조건을 사용한다.

```sql
WHERE title LIKE '%검색어%'
```

구현은
[`QuerydslAuctionListQueryRepository.titleContains`](../bidwin-back/src/main/java/com/tikitaka/bidwinback/auction/infrastructure/QuerydslAuctionListQueryRepository.java#L919)에
있다.

선행 `%`가 붙은 부분 검색은 제목 B-Tree 인덱스로 검색 범위를 좁힐 수 없다.
현재 목록 쿼리는 추천, 최신, 마감, 가격순에 맞는 인덱스를 순회하면서 각
후보의 제목을 검사한다. 따라서 검색 결과가 적거나 정렬 인덱스의 뒤쪽에
몰려 있으면 필요한 결과를 찾기 위해 많은 후보를 검사한다.

이 특성 때문에 다음과 같은 tail latency가 발생한다.

- 흔한 검색어는 정렬 상단에서 결과를 빠르게 찾는다.
- 희귀 검색어는 결과를 찾기 위해 많은 후보를 검사한다.
- 검색 결과가 없으면 활성 경매 후보 대부분을 검사할 수 있다.
- 동일한 요청 구조에서도 검색어와 정렬에 따라 실행시간이 크게 달라진다.

현재 목록 조회는 정확한 `COUNT`를 수행하지 않고 조회 가능한 페이지 상한을
사용한다. 관련 구현은
[`AuctionListService.getList`](../bidwin-back/src/main/java/com/tikitaka/bidwinback/auction/application/AuctionListService.java#L38)에
있다. 따라서 이번 개선의 주요 대상은 `COUNT`가 아니라 검색어가 포함된
목록 후보 조회다.

## 요구사항

- 한글, 영문, 숫자가 포함된 제목의 중간 문자열을 검색할 수 있어야 한다.
- 활성/종료 상태, 경매 유형, 카테고리 필터를 유지해야 한다.
- 1차 검색은 추천, 최신, 마감임박 정렬을 지원해야 한다.
- 검색어가 없는 목록은 낮은 가격, 높은 가격 정렬을 계속 지원해야 한다.
- 지원하는 검색어에서는 기존 `LIKE` 검색과 동등한 결과를 제공해야 한다.
- 경매 등록 직후 검색 결과에 반영되어야 한다.
- 별도 검색 시스템 도입 없이 현재 운영 환경에서 관리할 수 있어야 한다.

## 검토한 대안

### 1. MySQL n-gram 전문 검색

MySQL의 n-gram parser는 한글을 포함한 CJK 문자열을 연속된 `n`개 문자
단위로 분리하고, InnoDB FULLTEXT 역색인에 저장한다. 검색 시 전체 후보의
제목을 순차 검사하지 않고 검색어의 토큰에 대응하는 문서 ID를 먼저 찾을 수
있다.

예상 형태는 다음과 같다.

```sql
CREATE FULLTEXT INDEX idx_auction_title_ngram
    ON auction (title) WITH PARSER ngram;

SELECT id
FROM auction
WHERE MATCH(title) AGAINST (? IN BOOLEAN MODE)
  AND /* 상태, 유형, 카테고리 조건 */
ORDER BY /* 요청 정렬 */
LIMIT ?;
```

장점:

- 기존 MySQL을 그대로 사용하므로 별도 검색 클러스터가 필요하지 않다.
- MySQL 데이터와 검색 인덱스 사이의 별도 동기화가 필요하지 않다.
- 선행 와일드카드 검색을 역색인 기반 후보 조회로 변경할 수 있다.
- 현재처럼 제목 한 필드만 검색하는 요구사항에 필요한 기능을 제공한다.

제약:

- FULLTEXT 인덱스의 저장 공간과 경매 등록 시 색인 비용이 추가된다.
- 검색 후보가 매우 많은 고빈도 검색어는 필터링과 정렬 비용이 여전히 클 수
  있다.
- FULLTEXT 인덱스와 기존 정렬 인덱스를 하나의 쿼리에서 모두 효율적으로
  활용하지 못할 수 있으므로 모든 정렬에 대해 `EXPLAIN ANALYZE`가 필요하다.
- 기존 `LIKE`와 FULLTEXT의 공백, 특수문자 및 검색어 해석이 다를 수 있다.
- `ngram_token_size` 변경은 서버 설정과 인덱스 재생성이 필요하다.

MySQL 8.4의 기본 `ngram_token_size`는 2다. 2글자 이상의 부분 문자열 검색을
기본 정책으로 삼고, 한 글자 검색은 제한하는 방안을 우선 검토한다. 자연어
검색은 분리된 토큰 중 일부만 일치해도 결과를 반환할 수 있으므로 Boolean
phrase 검색 또는 최종 `LIKE` 재검증으로 기존 부분 문자열 의미를 보장해야
한다.

### 2. Elasticsearch 또는 별도 검색엔진

Elasticsearch는 오타 허용, 형태소 분석, 자동완성, 검색 점수 조정, 다중 필드
검색과 독립적인 수평 확장에 유리하다. 하지만 현재 요구사항에서는 다음
비용이 추가된다.

- MySQL 원본과 검색 인덱스 사이의 동기화 지연과 불일치 가능성
- dual write 대신 outbox 또는 CDC를 구성하고 실패 이벤트를 재처리하는 체계
- 초기 backfill, 전체 재색인 및 매핑 변경 절차
- 별도 클러스터의 배포, 모니터링, 보안, 백업 및 장애 대응
- 검색 장애 시 fallback 또는 기능 저하 정책
- 운영 가능한 고가용성 구성을 위한 별도 컴퓨팅 및 저장 공간

100만 건이라는 데이터 수만으로 Elasticsearch가 반드시 필요한 것은 아니다.
현재처럼 짧은 제목의 부분 검색만 필요하다면 검색 성능 이점보다 운영
복잡도가 더 크게 증가한다. 다만 검색 부하를 MySQL에서 분리해야 하거나 고급
검색 요구사항이 추가되면 가장 먼저 다시 검토할 대안이다.

### 3. 한글 자모 분해

예를 들어 `가격`을 `ㄱㅏㄱㅕㄱ`으로 변환해 별도 컬럼에 저장하는 방식이다.
이는 초성 또는 자모 검색을 위한 정규화 방법이며, 그 자체가 인덱싱 전략은
아니다.

분해한 문자열을 다음과 같이 조회하면 선행 와일드카드 문제는 그대로 남는다.

```sql
WHERE decomposed_title LIKE '%ㄱㅏㄱ%'
```

자모 검색이 실제 요구사항이라면 정규화한 값에도 별도의 FULLTEXT 또는
역색인이 필요하다. 현재 요구사항에 초성/자모 검색이 없으므로 우선 도입하지
않는다.

### 4. B-Tree 기반 prefix 검색

검색을 `LIKE '검색어%'`로 제한하면 일반 B-Tree 인덱스를 활용할 수 있다.
구현과 운영 비용은 가장 낮지만 제목 중간에 있는 단어를 검색할 수 없으므로
현재 검색 경험을 유지할 수 없다.

### 5. 별도 n-gram 매핑 테이블

제목을 애플리케이션에서 토큰으로 분리하고 다음과 같은 테이블을 운영할 수
있다.

```text
auction_title_ngram(token, auction_id)
```

`(token, auction_id)`에 B-Tree 인덱스를 만들면 검색은 가능하지만 다음 구현을
직접 책임져야 한다.

- 제목 등록 및 변경 시 토큰 동기화
- 여러 토큰의 교집합 계산
- 중복 토큰 및 삭제 처리
- 저장 공간과 쓰기 증폭 관리
- backfill 및 재생성 절차

이는 MySQL FULLTEXT가 제공하는 역색인을 직접 구현하는 방식이므로 선택하지
않는다.

### 6. 검색 결과 캐시

인기 검색어의 반복 요청에는 효과가 있지만 희귀 검색어와 결과가 없는 검색의
첫 요청은 개선하지 못한다. 상태와 가격이 지속적으로 변경되는 경매 특성상
무효화 정책도 복잡해진다. n-gram 적용 후 실제 검색 패턴이 확인되면 보조
최적화로 검토한다.

## 초기 선택 근거

실험 전 MySQL n-gram 전문 검색을 1차 후보로 선택한 근거는 다음과 같다.
후속 성능·안정성 검증에서 현재 구현의 도입은 철회했으며, 아래 내용은 초기
가설을 보존한 기록이다.

1. 현재 병목인 선행 와일드카드 후보 검사를 역색인 조회로 변경할 수 있다.
2. 제목 한 필드의 부분 검색이라는 현재 요구사항을 충족한다.
3. 기존 MySQL 트랜잭션 안에서 데이터와 검색 인덱스의 일관성을 유지한다.
4. 별도 클러스터와 색인 이벤트 파이프라인을 운영하지 않아도 된다.
5. 향후 요구사항이 확장되면 Elasticsearch로 이전할 수 있는 단계적 선택이다.

## 성능 검증 시나리오

### 데이터 구성

- 전체 경매 100만 건
- 활성 경매 30만 건, 종료 경매 70만 건
- UP/DOWN 경매와 카테고리를 실제 예상 비율로 분배
- 제목 길이, 단어 빈도 및 중복률을 실제 서비스와 유사하게 구성
- 모든 제목을 무작위 고유 문자열로 만들지 않고 일부 단어는 Zipf 형태로
  반복되도록 구성
- 동일한 seed로 현재 `LIKE` 방식과 n-gram 방식의 데이터를 일치시킴

### 검색어 유형

| 유형 | 목적 | 예시 조건 |
| --- | --- | --- |
| 고빈도 | 후보가 많을 때 필터·정렬 비용 측정 | 활성 경매의 10~30% 매칭 |
| 중빈도 | 일반적인 검색 측정 | 활성 경매의 약 1% 매칭 |
| 희귀 | 긴 후보 탐색 여부 확인 | 수십 건 매칭 |
| 결과 없음 | 최악의 후보 검사 측정 | 0건 매칭 |
| 정렬 상단 집중 | 조기 LIMIT 효과 확인 | 결과가 정렬 선두에 집중 |
| 정렬 하단 집중 | tail latency 재현 | 결과가 정렬 후미에 집중 |
| 경계 입력 | 검색 정책과 정확성 검증 | 한 글자, 공백, `%`, `_`, `!`, 따옴표 |
| 문자 조합 | collation 및 토큰화 검증 | 한글, 영문 대소문자, 숫자, 혼합 문자열 |

### 조회 조합

- 검색 방식: 현재 `LIKE` / MySQL n-gram FULLTEXT
- 검색 정렬: 추천 / 최신 / 마감임박
- 비검색 회귀 확인: 낮은 가격 / 높은 가격
- 경매 유형: 전체 / UP / DOWN
- 상태: 활성 / 종료
- 페이지: 1 / 10 / 100
- 캐시 상태: cold / warm
- 동시 요청: 1 / 10 / 50

모든 조합을 동일한 DB 사양과 데이터로 실행한다. 각 테스트는 충분히
워밍업한 뒤 반복 실행하고 평균값보다 p50, p95, p99를 중심으로 비교한다.

### 측정 지표

- API 전체 응답시간 p50, p95, p99
- DB 쿼리 실행시간
- `EXPLAIN ANALYZE`의 실제 검사 행 수
- 정렬 대상 행 수와 임시 테이블 또는 filesort 사용 여부
- MySQL CPU, 디스크 I/O 및 buffer pool 사용량
- FULLTEXT 인덱스 크기와 생성 시간
- 경매 등록 및 제목 변경의 p95 응답시간
- 동시 검색 중 일반 경매 조회와 입찰 처리에 미치는 영향

### 잠정 통과 기준

- 지원하는 검색 입력에서 p95 500ms 이하
- 지원하는 검색 입력에서 p99 1초 이하
- 기존에 관찰된 2~3초 지연 제거
- 지원하는 검색어의 결과 ID와 정렬 순서가 기존 정책과 일치
- 페이지 간 결과 누락과 중복 없음
- 경매 등록 p95 성능 저하 10% 이내
- 운영 환경에서 수용 가능한 인덱스 크기와 DB 자원 사용량

수치는 검증 환경의 DB 사양과 실제 서비스 SLO에 맞춰 최종 확정한다.

## 적용 시 확인 사항

1. 검색 최소 길이를 2글자로 제한할지 결정한다.
2. Boolean phrase 입력에서 FULLTEXT 연산 문자를 안전하게 처리한다.
3. 공백, 특수문자, 영문 대소문자 및 한글 정규화 결과를 기존 검색과 비교한다.
4. 검색어가 없을 때는 현재 정렬 인덱스 기반 경로를 유지한다.
5. 검색어가 있을 때만 FULLTEXT 후보 조회 경로를 사용한다.
6. 세 가지 검색 정렬과 필터 조합에 대해 `EXPLAIN ANALYZE`를 확인한다.
7. 대용량 FULLTEXT 인덱스 생성 시간과 배포 중 DB 부하를 측정한다.
8. 적용 전후 쓰기 지연, DB CPU, I/O 및 인덱스 크기를 모니터링한다.

구체적인 코드 구조, 마이그레이션 및 배포 순서는
[경매 제목 n-gram 검색 구현 설계](./auction-search-ngram-implementation-design.md)를
따른다.

## Elasticsearch 재검토 조건

다음 중 하나가 발생하면 별도 검색엔진 도입을 재검토한다.

- MySQL n-gram 방식이 목표 p95/p99를 만족하지 못한다.
- 검색 트래픽이 MySQL의 입찰 및 경매 트랜잭션 성능에 영향을 준다.
- 제목 외 설명, 카테고리, 판매자 등 다중 필드 검색이 필요하다.
- 오타 허용, 자동완성, 동의어, 형태소 분석, 검색어 가중치가 필요하다.
- 검색 결과의 독립적인 수평 확장이 필요하다.
- 검색 데이터의 eventual consistency를 수용할 수 있다.
